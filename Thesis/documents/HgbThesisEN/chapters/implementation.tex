\chapter{Implementation}
\label{cha:Implementation}

This Chapter goes into detail about the implementation of the prototype created for the evaluation.
After providing an overview of the hardware and software used during the development, the different components of the program and the implementation details for the inpainting methods are explained in further detail.

\subsubsection{Hardware}

As the focus of this thesis lies on the evaluation of inpainting methodologies in an AR environment, a HMD which supports this technology,
as well as provides access to the camera-data is required. In addition, the HMD should have the capabilities of hand-tracking for the area selection component.

A Meta Quest 3\footnote{https://www.meta.com/en/quest/quest-3/} is chosen for this, as it provides all the necessary features, was just recently extended with its new passthrough API\footnote{https://developers.meta.com/horizon/documentation/spatial-sdk/spatial-sdk-pca-overview}, which allows
for developers to directly access camera data and was readily on hand. The HMD is equipped with two RGB cameras with 18 Pixels Per Degree for video see-through, whose output is displayed on two 2.064x2.208 pixel displays with a refresh rate of up to 120hz.

\subsubsection{Software}
The implementation is built in the Unity3D Game Engine\footnote{https://unity.com/products/unity-engine} in the Version 6000.1.0f1.
\\
It uses the Meta XR Core SDK\footnote{https://assetstore.unity.com/packages/tools/integration/meta-xr-core-sdk-269169} with the Version 83.0.1 and the Meta MR Utility Kit \footnote{https://assetstore.unity.com/packages/tools/integration/meta-mr-utility-kit-272450} with the similar version number for the integration of the Meta Quest 3 HMD and its APIs to the prototype.

The aforementioned Meta Passthrough API is built on top of the Android Camera2 API. This allows for the camera to be used in a similar manner to mobile phone cameras, albeit with a few caveats:

\begin{itemize}
\item As of this moment the passthrough API is not supported over link. This means the software can only be evaluated on device, in the Meta Quests' standalone mode.

\item The Camera Texture returned by the API is smaller than what a user sees in the Quest 3. Whilst there are extensions and improvement over time, as of this moment it is not possible to cover the entire viewport of the user.

\item The Camera Texture is inside of the GPU memory. For inpainting and the quality evaluation, this needs to be sent to the CPU which takes up additional latency \cite{MetaPassthrough}.\\
\end{itemize}

As for the Code itself, it is written in C\string# 9 on the .Net Standard 2.1. This version of the standard in theory supports all C\string# versions up to 10.0, but the version packaged with the Unity Game Engine only supports the language features up to C\string# 9.0 as of this moment \cite{UnityCSharp}.

The entire controlling of the system is handled within the AreaSelectionVisualizer class. This script receives the hand-tracking data from the AreaSelectionGestureHandler and then uses the SelectionUiController to visualize the selection area to the user.

as well as handing over all the data to the evaluation implementations.

The selection of which inpainting algorithm to use still happens inside of the AreaSelectionVisualizer class, which initializes the algorithm on program startup, or whenever the algorithm gets changed through the joystick on a controller. This was implemented to ease up the comparison of the inpainting methods by keeping the same mask between methodologies.

\section{Area Selection and Tracking}
As already mentioned in concept chapter about user input (see \ref{cha:UserInput}), hand-tracking is used for defining the inpainting mask.

For this, the skeleton of the hand and the positions for each of the fingers needs to be tracked reliably. The Meta XR Core SDK already provides the tracking capabilities and mapping of the users hand to a skeleton \cite{MetaOVRSkeleton}.

\begin{figure}[htb!]
  \begin{center}
    \includegraphics[width=1\textwidth]{OVRHandSkeleton.jpg}
    \caption{A visualization of the bones and joints tracked by the Meta XR Core SDK \cite{MetaHandtracking}}
    \label{fig:HandSkeleton}
  \end{center}
\end{figure}

The tracked bones and joints, as seen in \ref{fig:HandSkeleton} each have their own unique transformation in the world. By using the rotation vectors of these transformations, the direction of the fingers and therefore the angle between two fingers can easily be calculated. 
\begin{program}[h!]
\caption{Gesture Recognition method}
\label{prog:LShape}
\begin{CsCode}
private bool CheckLShape(OVRSkeleton skeleton, out Vector3 cornerPos) {                                                                                                                 
    cornerPos = Vector3.zero;                                                                                                                                                                            
    var bones = skeleton.Bones;                                                                                                                                                                                                                                                                                                                                                                           
                                                                                                                                                                                                         
    // Index Finger: Proximal (6) to Distal (8)                                                                                                                                                          
    var indexKnuckle = bones[6].Transform.position;                                                                                                                                                      
    var indexTip = bones[8].Transform.position;                                                                                                                                                          
                                                                                                                                                                                                         
    // Thumb: Metacarpal/Knuckle (Thumb1) Tip (Thumb3) more stable than proximal/distal                                                                                                                             
    var thumbKnuckle = bones[3].Transform.position;                                                                                                                                                      
    var thumbTip = bones[5].Transform.position;                                                                                                                                                          
                                                                                                                                                                                                         
    Vector3 indexVector = (indexTip - indexKnuckle).normalized;                                                                                                                                          
    Vector3 thumbVector = (thumbTip - thumbKnuckle).normalized;                                                                                                                                          
                                                                                                                                                                                                         
    float angle = Vector3.Angle(indexVector, thumbVector);                                                                                                                                               
                                                                                                                                                                                                         
    // Slight tolerance to allow for fingers to be slightly off angle                                                                                                                                    
    if (angle >= 75 && angle <= 105) {                                                                                                                                                        
        cornerPos = thumbKnuckle;                                                                                                                                                                        
        return true;                                                                                                                                                                                     
    }                                                                                                                                                                                                    
                                                                                                                                                                                                         
    return false;                                                                                                                                                                                        
}         
\end{CsCode}
\end{program}
 
In the example shown in \ref{prog:LShape}, the thumb and index finger are compared, based on the directional vector, created when comparing the position of the knuckle or proximal with the tip of the finger. If they have an angle of close to 90° between each other, they create an L-like shape, which can then be used as the border-point for the area selection.
As the base-bone of the thumb is the metacarpal, the rectangles corner is slightly closer to the wrist than the actual corner of the L. This stabilizes the gesture detection, albeit at the cost of a slight displacement.

By applying this method to both hands, the selection state can be confirmed. This ends up handing over the position in the users viewport to the inpainting logic, 
which then uses it for defining the area to mask of the image, as seen in \ref{fig:AreaSelectionDemo}.

The mask display is managed through a simple RectMask2D from Unity, which is positioned and resized according to the hand positions in the SelectionUiController.

Behind the RectMask2D component, a 2D Canvas can be found. This canvas is placed according to the camera position during the selection. After the selection, it needs to be rotated to always face the camera, as it is just a 2D display in the 3D Space.
\\
In case the camera moves away from the mask, causing it to be outside of the cameras view frustum, it is frozen in place to avoid any additional unnecessary performance degradation. This is accomplished by comparing the corner points of the mask to the cameras frustum.

\subsubsection{Rectangle to Image Pixel-Mapping}
For the inpainting algorithms, this mask rectangle needs to be converted into a list of pixels, which need to be inpainted by the algorithms. Since the mask does not change between frames this only needs to be calculated once.
Most algorithms need to regularly check if a pixel is within the masked area, a HashMap is used for its fast O(1) access when checking whether it contains a value.

For this conversion, the masks position first of all needs to be converted into texture coordinates, which are then used to calculate the array indices for the pixel array returned by the camera texture.

Both the mask and the current frame camera texture are then handed over to the inpainting algorithm for each frame.

\section{Inpainting Algorithm Implementation}

The Inpainting algorithms are being called each frame. The reason for this is to allow for an easy comparison of the performance by looking at the Frames per Second (FPS) the application achieves. The target FPS rate for real-time should be at least 60 FPS for HMDs to avoid motion sickness. For regular displays, 30 FPS should also be sufficient \cite{WangQile2023Asro}. 

As both the NLTM and ELTM algorithms require downscaling, this too is applied to the FMM and the LaMa methods to keep the input to the algorithms similar. The default resolution of 1280x1280 would mean 100k+ iterations for the texture matching algorithms for the candidate evaluation, which would make both methodologies infeasible for real-time inpainting with current hardware, however by simply downscaling the image and upscaling it again after the inpainting algorithm finished,
the performance can be improved majorly. As the inpainting aims to overlay objects with background predictions, which are not in the focus for the user, the quality loss is acceptable and should still be superior in quality compared to FMM due to the texture recognition.

\subsubsection{Unity Burst Compiler}
Since the Mono runtime of unity is rather slow for such high performance implementations, the Unity3D Engine provides the Burst Compiler\footnote{https://docs.unity3d.com/Packages/com.unity.burst@1.8/manual/index.html}.

This compiler works by translating the Intermediate Language code generated by C\string# into code specifically generated for the target CPU architecture by using LLVM\footnote{https://llvm.org/}, which can lead to a 10x - 100x performance improvement, similar to writing raw C/C++ code.
Since the LLVM translation layer does not support the full C\string# language scope, Burst code needs to be written in a specific pattern and marked with the [BurstCompile] Attribute.

In terms of the code written, it can be seen as similar to C in its approach. It only supports structs, needs manual memory management and only offers very simple data structures. It is commonly used in the Unity Job system and
requires a similar approach for calling it in a method, although it is also possible to compile static methods using the burst compiler \cite{SchönerBurst}.

In the FMM inpainting implementation the job for the initialization is called, as seen in \ref{prog:FmmInitJob}.

\subsubsection{Fast Marching Method}

\begin{program}[h!]
\caption{Fast Marching Method MinHeap Stale Entry handling}
\label{prog:FMMHeap}
\begin{CsCode}
private static void RunFmmWithHeap(...) {
    while (heap.Length > 0) {
        var node = heap.Pop();
        int idx = node.Index;
        // Skip if this is a stale entry (generation mismatch)
        if (node.Generation != generations[idx]) continue;
        ...
        // All Neighbors
        for (int i = -1; i <= 1; i++) {
            for (int j = -1; j <= 1; j++) {
                if (i == 0 && j == 0) continue;
                int nbY = y + i;
                int nbX = x + j;
                if (nbY < 0 || nbY >= height || nbX < 0 || nbX >= width) continue;
                int nbIdx = nbY * width + nbX;
                ...
                // Solve eikonal
                float newDist = SolveEikonalQuadrants(ref distanceMap, ref flags, nbY, nbX, width, height);
                if (newDist < distanceMap[nbIdx]) {
                    distanceMap[nbIdx] = newDist;
                    // Old entries with lower generation will be skipped
                    generations[nbIdx]++;
                    heap.Push(new FmmNode
                        { Distance = newDist, Index = nbIdx, Generation = generations[nbIdx] });
                }
                ...
            }
        }
    }
}
\end{CsCode}
\end{program}


In addition to the aforementioned burst compilation and parallelization, any stale entries during the inpainting iterations are skipped. This is in regards to the reference pixel distance, which gets updated for neighbor pixels in case the eikonal function result is lower than the prior distance. 
In the default algorithm, the specific entry inside the heap would need to be looked for and updated accordingly. In this implementation, a new entry is simply added to the heap, as can be seen in \ref{prog:FMMHeap}.

To find out if a heap entry is stale, an id is stored with the heap entry. For each pixel to inpaint, the most current id is stored inside of a separate data structure for reference. If this id does not match the entry is declared stale, reducing the asymptotic runtime of the distance update from O(n) to O(log n)

\subsubsection{Nonlocal Texture Matching and Nonlinear Filtering}
\label{cha:NLTMImpl}

As already mentioned in the Concept chapter (see \ref{cha:InpaintingDesign}), the NLTM algorithm by itself is rather slow. 

One of the proposed optimizations was the PatchMatch-oriented approach of looking for subsequent frames candidates within the surroundings of the prior frames candidate pixel patches. One advantage of this is the possibility of parallelizations, as the candidate patches are all independent of one another.
Therefore this can once again be solved through the implementation of a IJobParallelFor as seen in \ref{prog:NltmCachedPositions}

\begin{program}[h!]
\caption{Nonlocal Texture Matching cached candidate patch search}
\label{prog:NltmCachedPositions}
\begin{CsCode}
// Parallel job for searching specific positions
[BurstCompile]
private struct SearchPositionsJob : IJobParallelFor {
    ...

    public void Execute(int index) {
        int pos = SearchPositions[index];
        int sx = pos % Width;
        int sy = pos / Width;
        // candidate Patches which contain parts of the mask are not valid
        if (!IsPatchFullyKnownBurstStatic(sx, sy, MaskSet, Width, Height)) {
            Results[index] = new CandidateInfo { Index = -1, Distance = float.MaxValue };
            return;
        }
        float distance = CalculateTextureDistanceBurstStatic(
            TargetX, TargetY, sx, sy, MaskSet, Pixels, GaussianWeights, Width, Height);
        if (distance >= 0) {
            Results[index] = new CandidateInfo { Index = pos, Distance = distance };
        } else {
            Results[index] = new CandidateInfo { Index = -1, Distance = float.MaxValue };
        }
    }
}
\end{CsCode}
\end{program}

The NLTM Implementation is only configured to use the best 4 candidate patches for the alpha trimmed mean values.
This means the found candidates for each target patch need to be sorted in order of the texture similarity. As there is a very large number of candidates, of which only the best 4 are required, the overhead of sorting any more candidates is unnecessary.

Therefore the sort algorithm only uses a partial sort, using the selection sort algorithm, as it is the easiest to implement using deconstruction in C\string#, as can be seen in \ref{prog:NLTMSort}.

\begin{program}[h!]
\caption{Nonlocal Texture Matching candidate Patch Partial Sort}
\label{prog:NLTMSort}
\begin{CsCode}
private static void SortCandidates(ref NativeList<CandidateInfo> candidates) {
    int n = candidates.Length;
    // Only find the K smallest using partial selection in the sort, stop sort afterwards
    for (int i = 0; i < K; i++) {
        int minIdx = i;
        float minDist = candidates[i].Distance;
        for (int j = i + 1; j < n; j++) {
            if (candidates[j].Distance < minDist) {
                minDist = candidates[j].Distance;
                minIdx = j;
            }
        }
        // Swap minimum to position i
        if (minIdx != i) {
            (candidates[i], candidates[minIdx]) = (candidates[minIdx], candidates[i]);
        }
    }
}
\end{CsCode}
\end{program}

By simply using these optimizations, the Time Per Pixel, which was tracked during the implementation to measure how much time the inpainting algorithm takes in correlation to the pixel count of the mask was reduced by \string~10x

\subsubsection{Exemplar-Based Image Inpainting with modified priorities}

The implementation of this algorithm is in large parts similar to the NLTM Algorithm presented in \ref{cha:NLTMImpl}, although there are several large changes:

\begin{itemize}
    \item The Priority Function was overhauled according to the thesis presented in \ref{cha:ELTMTheory}. Due to these changes, the fill order of the masked area stays accurate and does not degrade. This means the patches targeted for inpainting are of higher quality and the overall filled area should be more consistent.
    \item Instead of using an alpha trimmed mean value for the pixels, the best patch is picked. This makes the algorithm a lot more performance, albeit at the cost of artifacts in case the best matching patch contains any noise or artifacts.
    \item Whilst the NLTM Algorithm used a performance heavy gaussian-weighted distance for its candidate selection, whilst ELTM uses a simple sum of squared differences. This means ELTM will be worse for matching textures, but in return it should provide superior performance.
    \item The candidate search is limited to a local area instead of the entire image, although the modified NLTM algorithm uses a similar approach, albeit using the local area of the prior frames candidate patches rather than the target patches local area.
\end{itemize}

The local search can once again be implemented as a parallel job, allowing for full parallelization in the candidate search, as seen in \ref{prog:ELTMcandidateSearch}.

\begin{program}[h!]
\caption{Exemplar-Based Image Inpainting local candidate search}
\label{prog:ELTMcandidateSearch}
\begin{CsCode}
[BurstCompile]
private struct LocalSearchJob : IJobParallelFor {
    ...

    public void Execute(int i) {
        int pos = SearchPositions[i];
        int sx = pos % Width;
        int sy = pos / Width;
        if (!IsPatchFullyKnownStatic(sx, sy, MaskSet, Width, Height)) {
            Distances[i] = float.MaxValue;
            return;
        }
        Distances[i] = CalculateSsdStatic(TargetX, TargetY, sx, sy, MaskSet, Pixels, Width, Height);
    }

    ...
    
    [MethodImpl(MethodImplOptions.AggressiveInlining)]
    private static float CalculateSsdStatic(int targetX, int targetY, int sourceX, int sourceY,
        NativeParallelHashSet<int> maskSet, NativeArray<Color32> pixels, int width, int height) {
        float sum = 0f;
        int cnt = 0;
        for (int dy = -PatchRadius; dy <= PatchRadius; dy++) {
            for (int dx = -PatchRadius; dx <= PatchRadius; dx++) {
                ...

                Color32 targetColor = pixels[targetIdx];
                Color32 sourceColor = pixels[sourceIdx];
                float diffRed = targetColor.r - sourceColor.r;
                float diffGreen = targetColor.g - sourceColor.g;
                float diffBlue = targetColor.b - sourceColor.b;
                sum += diffRed * diffRed + diffGreen * diffGreen + diffBlue * diffBlue;
                cnt++;
            }
        }
        return cnt > 0 ? sum / cnt : float.MaxValue;
    }
}
\end{CsCode}
\end{program}
Each patch gets its texture distance calculated accordingly, of which the patch with the lowest distance and therefore the highest similarity is picked and used to fill out the missing pixels of the target patch with the correlating pixels of the selected source patch.

\subsubsection{Large Mask Inpainting Model Integration}

As training a new inpainting model lies out of scope for this thesis, the provided model\footnote{https://github.com/advimman/lama} which was trained by the original LaMa authors back in 2021 for their paper (see \cite{SuvorovRoman2022RLMI}) was used.

The Unity developers created the Sentis library for the integration of pretrained neural network models into applications for real-time use. This library also allows for those models to be ran directly on the GPU \cite{UnitySentis}.

This library only offers support for models in the Open Neural Network Exchange (ONNX) format, whilst the provided LaMa model is merely a Checkpoint file. Therefore this model needs to be converted accordingly. This has already been implemented by Carve-Photos, who provided a python script\footnote{https://github.com/Carve-Photos/lama/tree/main} to export the model to ONNX.

By using this script and exporting the model with the Opset-Version 15, it can then be imported by the Sentis engine during the applications runtime, as seen in \ref{prog:LaMaImport}.

\begin{program}[h!]
\caption{LaMa Model Initialization}

Both the source image and the inpainting mask are both put into the model through tensors.
The size of these needs to be defined during the ONNX export and has been set to 256x256 pixels for the evaluation. Therefore the input texture and mask need to both be downscaled accordingly and upscaled afterwards, similarily to the NLTM and ELTM implementations.

Running the model is just as simple, with just a few lines of code, as seen in \ref{prog:LaMaInference} to create the tensors and schedule the model run. The result can then be retrieved by the PeekOutput method, which blocks the thread until the model finishes

\begin{program}[h!]
\caption{LaMa Model Inference}
\label{prog:LaMaInference}
\begin{CsCode}
private Tensor<float> RunInference() {
    // Create fresh tensors from pre-filled arrays
    // Tensors become GPU-bound after inference and can't be rewritten
    var imageShape = new TensorShape(1, 3, ModelSize, ModelSize);
    var maskShape = new TensorShape(1, 1, ModelSize, ModelSize);
    using var imageTensor = new Tensor<float>(imageShape, m_imageData);
    using var maskTensor = new Tensor<float>(maskShape, m_maskData);

    m_worker.SetInput("image", imageTensor);
    m_worker.SetInput("mask", maskTensor);

    m_worker.Schedule();

    var gpuTensor = m_worker.PeekOutput() as Tensor<float>;

    // Download from GPU to CPU - ReadbackAndClone returns a new CPU-readable tensor
    var cpuTensor = gpuTensor.ReadbackAndClone();
    return cpuTensor;
}
\end{CsCode}
\end{program}

This output tensor then gets converted back into an array of Color values, which is then used to create a new texture for Unity to handle.

In terms of implementation complexity, it was by far the easiest to integrate, albeit due to the reason of all the complexity lying underneath inside of the training data of the model.

\section{Evaluation Background Jobs}

As the quality and clutter evaluation algorithms need a lot of computational resources they cannot run in the foreground for each frame, due to it affecting the performance evaluation severely. Therefore, the Unity Job System is used for these evaluations, albeit with the jobs running in the background rather than blocking the main thread like in the inpainting implementations.

This means the quality and clutter evaluation works on a "evaluate if ready" principle, only evaluating frames whenever there is no other frame being evaluated at the moment of the call, as seen on \ref{fig:EvaluationBackgroundSchedule}.

Whilst this reduces the consistency of the evaluation results slightly, it solves the issue of the evaluation impacting the performance of the rest of the program, as it is evaluated in a background-thread.

\section{Limitations}

As this implementation is meant as a prototype and the Meta Quest Passthrough API is still rather new, there are several limitations regarding the implementation:

\begin{itemize}
    \item The Meta Quest Passthrough API as of this moment only supports fixed, rather small camera feed textures, which do not contain all the content visible in the AR application background, which is applied to the skybox.
    This means, the inpainting area is limited around the middle of the users viewport and cannot quite reach the edges yet.

    \item In addition to the smaller size of the camera textures, they are applied on a 2D plane in the 3D space. Due to the AR background being applied to the skybox, it means the distortion, which is usually not visible on the skybox causes the overlay of the inpainted texture to be slightly offset in some cases.
    whilst this could be avoided by calculating the correction transformation and applying it, this would be out of the scope of this thesis, as it is not too visible on the inpainted areas as long as the mask leaves some padding between the edges and the object to be removed

    \item The implementations of the inpainting algorithms and evaluations are built for the CPU (except for LaMa, as it can be ran on the GPU by setting a flag during the model initialization),
    due to the large complexity and in part major rewrites which are necessary to get the algorithms and data structures to run on GLSL shader code instead of C\string#.

    \item The inpainting mask does not adjust to the objects behind it. This means, if a hand is placed behind the mask or the object behind the mask is moved, the mask will not adjust for the change, therefore painting over the hand or the now empty space. This could be solved by adjusting the mask dependant on the objects behind it,
    but this would once again add more performance degradations and complexity due to needing to track the objects movements and reacting to new objects added behind the mask.
\end{itemize}
